Pilsner

The verified-king arena: challengers serve their stack, the same fresh task battery runs against every entry on the same box, and the label is a pure function of the measured result.

Per-lane kings · replay-verified receipts · the >2% ratchet · github.com/buckZz7/pilsner

01 Why it exists

Ultra-compressed 27B-class models on one RTX 5090: the 2-bit class is genuinely good at agent work, and the 1-bit class isn't. Pilsner exists to measure that — on tasks that can't be memorized, with scores nobody can argue with.

A king is a measured result, not a claim. Beat it by more than 2% on a battery neither of you has seen, and you're the king. Equal or worse is a loss.

03 The arena

the king (model + serving stack)→ challenger PR→ fresh battery, same box→ one number→ beat by >2%?→ new king
One number. Success rate on the scored battery.
One rule. Beat the king by more than 2%. Equal or worse is a loss.
One tie-break. Time-to-task, measured same-box. Both better and faster wins; quality gates first.
Ratchet. The winner becomes the king, and the next challenger must beat them. The king is re-verified on a schedule.

Sequential per-PR — one challenger at a time, on the same 5090, against the same battery shape. The gates: size (one 5090, ≤32GB), quality floor (the ratchet), speed tier.

04 Verification

A receipt is admitted to the board only if replaying the recorded trajectory through the current domain code re-derives the claimed score. Forged, stale, and evidence-less receipts are refused — every refusal so far has been a true refusal.

tau2 run→ trajectory + results hash→ fresh env per sim, replay→ re-derive score→ admit or refuse

The receipt carries full provenance: spec version + sha, public seed, bundle sha, results sha. Anyone can regenerate the bundle from the seed and replay the trajectory themselves.

05 Why the score is trustworthy

Fresh batteries

Every eval re-emits the bundle from a fresh public seed (chain-rule seeds derive from the previous verified receipt). Memorizing one bundle buys nothing for the next.

Collusion guard

The user simulator is a fixed model, never the evaluated model — the eval can't frame its own test.

Execution-verified

Tasks succeed only if the work is actually done in the simulated world — booking canceled in the window, escrow released only after payment. No LLM judge to charm.

Same-box measurement

Quality and speed measured on the same hardware for every entry. Reproducible from the receipt: model, endpoint, seed, task set, τ² commit, wall clock.

The 1-bit's failure is not a JSON problem and not context drift: 93 of its 95 tool errors are User <id> not found — the agent must derive an entity id once and reuse it, and the 1-bit regenerates a guessed variation from the first reuse onward. Grammar-constrained decoding can't fix it (the calls are well-formed; the values are wrong). Entity derivation through ultra-low-precision weights. The BenchBrew lanes now measure the same axes at the honest operating point, with freshness and verification layered on.

07 The system

pilsner

This repo — the scorekeeper. Batteries, replay verification, chain-rule seeds, the verified-only board.

benchbrew

The factory. Specs → fresh, LLM-free task bundles, emitted into τ². Pilsner consumes evals it never wrote.

tau2-bench

The runtime — the orchestrator that executes the emitted domains.

Three separate repos, three jobs: factory, runtime, scorekeeper. Independence is a property of the system, not a claim about it.
